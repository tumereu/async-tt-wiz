# Runtime, randomness and verification profile

Technical completion under D-284; no scaffold, dependencies or executable tests
are created. Parameters are initial engineering defaults to validate, not measured
results or new game/history limits. [Protocol](protocol-v1.md) and
[storage mechanics](storage-mechanics.md) own consistency and recovery.

## Deterministic random input v1

Fresh invocation entropy: Android/JVM `SecureRandom` through platform adapters,
32 independent bytes per Shuffle; never time, object hash, ambient Kotlin Random
or a reused session seed. Server start uses independent seeds for each Library and
starter resolution. Shared deterministic processing never acquires entropy.

`shuffle-v1` seed is 32 bytes encoded base64url without padding (43 characters),
strictly decoded/re-encoded to reject noncanonical encodings. Sort actual member
UUIDs by unsigned 16-byte order. Produce a stream of SHA-256 blocks:

`SHA256(UTF8("async-tt-wiz/shuffle/v1\u0000") || seed || uint64be(counter))`

Counter starts at zero; concatenate blocks, read successive unsigned 32-bit
big-endian words. To sample bound b (1≤b≤2^31−1), let
`limit=floor(2^32/b)*b`; reject words u≥limit and return `u mod b` otherwise.
For i=n−1 down to 1 swap members i and `sample(i+1)`. Empty/single Libraries have
no swaps. Record concrete accepted order and algorithm/input in the server result.
Do not compare predicted membership as a new live Shuffle guard. D-278 stores
input in process memory, not a crash-durable journal; accepted input/order is durable
on the server. Replay/Redo uses that order, never resamples.

Die/coin acquisition uses the same unbiased bounded sampler over secure random
words, independently per invocation; coin sample 0/1, die sample 1..sides. Server
checks operation/count/ranges and records the supplied samples, not a second roll.
Random starter uses an independently domain-separated server seed/stream
`async-tt-wiz/starter/v1\u0000`, same counter/sampler; sort participant UUIDs and use
sample(2). Selection of Random alone never samples. Initialization outcomes commit
once at actual game start. This is reproducibility, not honest-client proof.

Required golden fixture set before implementation acceptance: seed all-zero,
incrementing bytes 00..1f, all-ff; empty/one/2/7/60 and 257 shuffled identities;
permuted source iteration; raw sampler words at 0, limit−1, limit, 2^32−1 for
b=1,2,3,7,2^31−1. Golden files must contain literal generated bytes, sampled words
and final IDs verified by an independent reference calculation, not expected values
computed at runtime by the same implementation under test. SHA-256 known-answer
fixtures supplement target parity. Initial literal SHA/sampler/seven-card/UUID
vectors are [recorded separately](../05-verification/random-v1-vectors.md); expanded
large fixtures belong to the later executable suite, not a new algorithm choice.

## Runtime and packaging

### Text, numeric and count encoding

Approved edge trimming uses Unicode White_Space code points (pinned Unicode 15.1
table for semantic v1); preserve interior text. Numeric whole-string grammar is
ASCII `[+-]?[0-9]+`, optionally one `/` joining two such whole strings for corner
pairs. No interior whitespace, decimal/exponent or locale-digit interpretation.
Compute exact arbitrary-precision integer +/-; normalize only changed numeric
components to base-10 without leading plus/zeroes (`-0` becomes `0`). Preserve an
unchanged pair component verbatim; Set stores its approved trimmed text rather than
numeric canonicalization. There is no game-rule clamp or fixed 32/64-bit overflow.
Text size bound still applies; an arithmetic result exceeding it rejects that
individual operation without truncation. Relative operations parse authoritative
current text, not a stale numeric cache. Pattern grammar does not apply to passwords,
emails, import syntax or chat.

Count operands are nonnegative whole decimal strings (die sides positive); clamp
Draw/View/Reveal quantities against actual available cardinality under their
contracts **before** allocating/iterating, not against an invented gameplay cap.
Die sides range 1..2147483647, default 6, exactly one result per invocation; coin
0/1 is displayed as heads/tails by the recorded mapping 0=heads, 1=tails. Bounds
are protocol resource/type limits, not new dice modes or secret min/max defaults.

## Application container interface

Runtime inputs: `DB_URL`, `DB_USER`, `DB_PASSWORD_FILE`, `PUBLIC_BASE_URL`,
`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD_FILE`, `MAIL_FROM`,
`MAIL_TOKEN_KEY_FILE` (encrypts token-bearing pending email only),
optional `FCM_CREDENTIALS_FILE`, and resource/observability overrides below.
No production credentials/default email relay. Secrets are files injected by the
external deployment repository. TLS termination/trusted proxy networks are operator
configuration; trust forwarded headers only from configured proxies. Service
listens on configurable port (default 8080), binds health endpoints separately from
public APIs as deployment permits, and does not embed production host/volume paths.

`/health/live`: process responsive, no secret/data detail. `/health/ready`: database
reachable, supported Flyway schema, writer ownership and workers ready. Until ready,
no command admission. Migration runner is one explicit startup job/command using
the same image; service validates schema and refuses incompatible schema, never
auto-creates tables. Run jOOQ generation against disposable migrated PostgreSQL.
On SIGTERM stop new admission, commit/roll back active transactions, flush committed
outbox publication best effort and stop within 30 seconds. Pending durable inbox/
outbox resumes on restart; shutdown does not wait indefinitely for notifications.

Durable inventory: PostgreSQL accounts/auth verifiers, decks/contacts/lifecycle,
root/definitions/tree/controls/exposures/outcomes/inbox/outbox. Baseline chunks and
checkpoints are rebuildable; caches are not backup substitutes. SMTP/FCM/signing/
database secrets are external. Production Compose/proxy/TLS/deploy/backup/erasure
orchestration stays external (D-272); no RPO/RTO or Pi capacity is promised here.

## Bounded input and backpressure defaults

Advertise negotiated limits in `welcome`; retain original request on transient
admission failure while process lives. Stop accepting **new** actions if capacity
is exhausted, show network/busy state, never drop old in-memory commands silently
or create an offline queue. No routine per-action final-result waits.

| Resource | Initial bound / action |
| --- | --- |
| Ordinary socket command | 1 MiB decoded UTF-8, depth 32; reject before admission on excess. Submit prepared-deck definitions by ordinary HTTP POST rather than huge per-action snapshots. |
| Client outgoing memory | 256 requests or 4 MiB; backpressure only at exhaustion. Retained reconnect sends in original order. |
| Server game mailbox/inbox backlog | 1024 not-yet-final requests per game, bounded 8 MiB pre-admission decoded mailbox. Pause socket reads or `busy` without receipt; do not accept and discard. |
| Action ingress rate | Token bucket 30 requests/sec/installation, burst 120; 120/sec/account burst 240. Typical bulk operations pipeline without artificial group delay; tune if approved normal operations hit it. |
| HTTP reads | 60/min/account expensive baseline/export starts separately 2/min and 2 active transfers/account; normal small reads 600/min. 429 gives retry hints. |
| Prepared/imported definition record | 256 KiB text metadata, 64 faces/record, 64 KiB per text field, safe image references only. Send the complete needed definition set in one ordinary JSON HTTP POST with normal HTTP-library/server request handling; validate all before installing it. No application-level chunks/pages/upload completion protocol (D-289). |
| Image | 10 MiB compressed bytes, 4096×4096 / 16 Mpixels decoded; bounds checked before bitmap allocation, no executable SVG/HTML. Oversize/invalid image falls back to text. |
| Client disposable artwork | 256 MiB disk LRU, decoded memory min(64 MiB, 1/8 app heap), downsample to scene need. Essential definitions/accepted history are not art cache. |

These are abuse/engineering limits, not approved limits on Stack size, game length,
cards played or retained branch count. If a valid ordinary use case cannot fit,
chunk it or raise the engineering bound after measurement; never silently omit
objects/branches or truncate an approved action. Input rejection is explicit and
must not be reported as an accepted partial deck update.

Use the compact canonical Stack checksum guard from protocol v1 rather than
shipping a whole entry list on every addition. Libraries/Stacks/tables are expected
to be modest in normal play; qualify realistic workloads before adding machinery
for hypothetical extreme sizes. Keep the existing chunked complete-history transfer
separate. No new generic command-fragment/dependency protocol or gameplay count cap
is selected by this review.

Bound each subscriber's queued delivery to 256 messages or 4 MiB initially; a slow
consumer is disconnected and recovers durable revisions/outcomes normally, without
blocking other games or losing a commit. This is a queued-byte budget, not a new
4-MiB gameplay transition limit. Do not eagerly materialize an unbounded outbox or
history in memory. A single large revision/result uses streamed ordinary HTTP
revision/result recovery rather than endless socket enqueue/disconnect retries;
stage accepted changes and apply them atomically. Unsupported oversized input gets
an explicit failure before mutation; if normal approved workloads hit engineering limits, fix representation/
capacity and requalify instead of silently truncating or adding a Stack/Library cap.

## Verification matrix and initial budgets

Performance is measured with animations enabled and no test-only dispatch APIs.
Reference baseline: API-29 arm64 physical phone, 4 GiB RAM/60 Hz/1080-class screen;
record exact model/build for reproducibility. Also current stable Android phone,
API-29 non-GMS emulator, current-API non-GMS emulator and ≥8-inch tablet; hardware
availability/model selection is lab logistics, not an extra product feature. Server
benchmark profile: 2 CPU cores/2 GiB app RAM, PostgreSQL separate 2 GiB allocation,
SSD; amd64 plus arm64 smoke/functional run. No inference of capacity for an unknown
Raspberry Pi. CI emulator performance is not physical-device frame evidence.

Use synthetic catalog/art through normal downloader and normal APK. Every E2E
gameplay/history setup uses actual UI; only lower model/protocol/performance layers
may synthesize 10k/100k-node sparse/heavily branched histories and large link/effect
fan-out. Failure controls manipulate traffic/process/storage externally, not game
rows or outcomes. Include empty/60/250-member Libraries, 200 visible objects and
400 links/projections; stress larger sizes without claiming product caps.

Starting targets under unloaded baseline, warm ordinary state: local provisional
feedback p95 ≤50 ms after gesture recognition; enqueue/write start p95 ≤50 ms with
no intentional batching wait; render p95 frame ≤16.7 ms and p99 ≤33.3 ms at 60 Hz;
server simple command p95 ≤100 ms; remote committed visible target p95 ≤250 ms on
50-ms RTT/no-loss network. Measure recognition delay separately for normal-mode
double tap. Cold accepted 10k-node current-game open ≤3 sec after bytes are local;
100k-node complete transfer must stream without OOM (no network-independent total
download deadline). Resource exhaustion leaves coherent explicit failure, not false
completion. These are release engineering acceptance targets to investigate/fix,
not delivery SLAs; report measurements and any proposed relaxation to the owner,
never silently bypass a failed check.

Required suites: shared model/property/golden replay; protocol trace permutations;
real-PostgreSQL lock/fence/crash/migrations via Testcontainers; native Compose scene/
accessibility/gesture/animation tests; normal signed-test APK Appium/UiAutomator2
journeys with Docker Compose backend and SMTP/synthetic-source adapters. Run clean
and retained-data compatible-upgrade paths, wrong-version refusal, crash-loss versus
server-admitted durability, ordinary session revocation, optional-FCM denial/poll overlap, complete
branched recovery and D-277 rendered endpoint trajectories. No implemented coverage
or passing performance measurements are claimed.

Observability: request correlation ID, ingress/commit/revision lag, inbox age/depth,
baseline restart/bytes, digest mismatch, replay budget exhaustion, DB pressure,
mail/push failures, worker retry and UI frame/action latency. Never routine-log
auth/reset tokens, passwords, card faces/names, deck/chat content or full payloads.
No third-party analytics/crash-upload SDK is required; local redacted diagnostics
may be shared deliberately, not silently uploaded.
