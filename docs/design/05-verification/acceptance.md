# 8. Acceptance scenarios and verification

## 8.1 Core acceptance scenarios

These scenarios are proposed tests for the confirmed requirements. Each must
eventually have concrete fixtures, expected states, and assertions. D-243/D-244
require synthetic data/art and full E2E scenarios against the running real backend
and normal Android app, with backend reset between tests. Only user/saved-deck
initialization may bypass the UI; all other user actions and required E2E outcome
assertions use the UI. Direct API assertions belong to additional lower-level
tests, not a substitute E2E result. See the [test strategy](e2e-strategy.md).

D-182 requires connected game actions/shared controls in initial delivery.
Downloaded offline review remains; former offline action/queue fixtures below
are superseded, not hidden implementation obligations. Online latency hiding and
in-flight delivery recovery remain distinct from supporting offline gameplay.

**Current Undo/Redo oracle:** removal/reinsertion requires every later retained
event's relevant `(from, to)` tuple to remain identical within N, with no fork
at/after the target. Redo must preserve its own recorded transition too. Revealing
targets are excluded. Personal viewing cannot select/truncate eligibility (D-245).
Older stable scenarios below have been corrected or explicitly retired; do not
restore D-161 captured-parent or remembered-head controls from decision history.
D-230/D-231 fix the Undo target to the latest still-applied own action, without
skipping a blocked own target; later opponent actions are preserved under replay.
D-235 makes each player's per-game stack shared game state across their devices,
not device-local history or a single stack for both players. D-236 treats distinct
Undo requests as successive presses against current server state, not fixed-node
requests to discard after a same-account device acts. One request's delivery
retries still execute only once. Older D-161 pinned-transition fixtures do not
override this current selective-Undo policy.

**D-232 tree-edit precedence:** Undo/Redo edit the existing tree, without creating
branches or retaining the pre-Undo path as an explorer alternative. Older fixtures
requiring immutable ancestry, original-branch retention after Undo or automatic
post-Undo branching describe the superseded pointer model. D-223 filtering still
applies to actual branches; D-233/D-245 block Undo at/before any retained later
fork. D-258 deliberate activation/interruption/return clears both Redo queues;
the old D-234 stranded-but-retained example is superseded when the new fork comes
from that switch. Normal Undo/Redo and ordinary opponent edits do not trigger the
switch reset. Deleted review cursors fall to their parents;
surviving cursors remain at their revised nodes. Removed-record retention after
Redo-queue clearing remains privacy/storage work. Do not use old fixtures to require
the assistant's rejected revised-continuation/untouched-original design.

## 8.2 Additional required test layers

All automated layers use synthetic game data and artwork. Full-stack acceptance
follows the [E2E strategy](e2e-strategy.md); lower-level tests supplement rather
than replace it. Each scenario inherits its feature's approved scope; broad older
references to export, custom authoring or offline actions do not re-add excluded
features.

- **Model tests:** every generic action, validation error, container/order change,
  face/composite display, unchanged-field guarantee, and undo path.
- **Property tests:** acyclic trees, single active branch, no duplicate zone
  membership, deterministic replay, transactional all-or-nothing behavior.
- **Protocol tests:** stale revisions, idempotency mismatch, payload limits,
  pagination under concurrent writes, authorization, explicitly invalidated sessions
  and D-268's absence of idle/absolute session expiry.
- **Fault tests:** dropped/delayed/reordered requests, process termination,
  low storage, failed migrations, offline dependencies, partial image downloads.
- **Compatibility tests:** historical schema versions, migrated snapshots,
  supported Android versions, differing client versions in one game.
- **End-to-end tests:** normal Android instances for both players against a
  running real backend, reset for every independent test, dynamic synthetic data
  and art, setup-only user/deck convenience calls and otherwise UI-only actions.
  Cover entry/deck import through result acceptance/return to lobby, manual play,
  projections, branching/Undo/Redo, multi-device synchronization, offline read-only
  access, online connection-loss/restart recovery and Logout privacy. See the
  [initial full journeys](e2e-strategy.md#initial-full-e2e-journeys).
- **Operational/application boundary tests:** container/configuration compatibility,
  service restart mid-publication, outbox redelivery and credential revocation
  remain here. Production backup/restore rehearsal and deployment rollback are
  owned by the separate operations repository under D-272, against this project's
  persistent-state/migration/recovery contract; they are not implemented here or
  silently assumed unnecessary.

Delivery gates and implementation instructions are kept separately in
[the agent delivery workflow](../../agent/delivery-workflow.md).
