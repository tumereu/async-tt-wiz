# Arcanum Automatum in ATW: integration spec

How ATW hosts the Arcanum libraries (rules engine `arcanum-engine`, parser, card model). Library-side decisions
are in `arcanum-automatum.md` (§2, engine API §7.0). This spec was approved in direction (owner, 2026-11-02); each
phase became a rules-version change (SYS-031) with its catalog entries.

**Status: built, then replaced in part.** Phases I0–I4 were built (2026-11-02 to 2026-11-04) on ATW's own game model
with the engine as a pure function over it (I-D7). Since the switch-over (I-D54, I-D56 step D2) every game is the
engine's own state, the server runs the engine, Automatum is always on (I-D52) and players act only for themselves
(I-D56); the old model's code is deleted (`engine-responsiveness.md` R4) and the behaviour that holds is in the feature
catalog. What is left here is the decision record (§1), which code comments cite (I-D2); decisions that later ones
replaced or changed are marked **Superseded** or **Changed**, the unmarked ones still hold. The old sections §2 (how a
call works), §3 (phases I0–I4 and their "Built" notes), §4 (shared state ATW adds), §5 (the Automatum switch), §6
(catalog entries by phase) and §7 (open points) described only the deleted model and are removed; they are in git
history (`git show 98ca19610:docs/specs/arcanum-atw-integration.md`).

## 1. Decisions (owner, 2026-11-02)

| # | Decision |
|---|---|
| I-D1 | **Phases in order** I0 plumbing → I1 view → I2 casting and resolving → I3 abilities, lands, combat, steps → I4 Automatum-only controls (§3). I1 is the first thing players get. |
| I-D2 | **Card definitions are parsed on the device from the game's own card data** (the `CardDefinition` each game holds for its cards, which the server shares with both players), cached by that data's digest and the parser version. Every card in a game is covered and both players parse the same text; the catalog isn't involved. Everything meaningful about a card travels with the game, so fields the engine needs (oracle text, colour indicator, …) are part of that data (owner, 2026-11-02; replaces "from the client catalog"). Server-delivered definitions and hand-written overrides come later. **Changed by I-D54:** the server reads the game's decks (`EngineDecks`) and gives every device the definitions with the game. |
| I-D3 | **Automatic passing** (now part of the single I-D18 setting; the host passes for a player when `Engine.shouldPassFor(state, player)` says so): when `Engine.options` shows a player can't respond to anything, the engine passes priority for them at once. **Superseded by I-D56 (§6, §7):** a device passes by itself only for its own player (the response mode's Auto-skip); for the other player only when they could only pass, judged on public information. |
| I-D4 | **The Automatum switch** sits in the table's top bar (§5); playtesting decides whether it moves into Table actions. **Superseded by I-D52** (there is no switch). |
| I-D5 | **Players are chosen as targets from their life squares** (TRN-030); avatars aren't on the table. |
| I-D6 | **One cast panel:** the panel that chooses modes, X and optional costs also shows the suggested mana tapping for the current choices, updated as they change; tapping a mana source in it changes the tapping. Targets are chosen on the table in between (CR 601.2b–h order: choices, targets, payment). |
| I-D7 | **ATW keeps its own game state; the engine is a pure function over it.** ATW builds an engine state for each call, sends the engine's changes as ordinary actions, and stores the few engine fields of §4.3. The engine state is always rebuildable from ATW state (P3). **Superseded by I-D54:** the engine's state is the game state; ATW keeps only table state. |
| I-D8 | **A flow** is everything from one player action (cast, activate, pass priority, change step, answer) until the engine returns with nothing left to decide; it is open exactly while there is a continuation, and may take several engine calls (one per decision). **Changed by I-D54/I-D56:** a player's own open cast or choice is a draft sent as one submission; everything else is one event per acting point (I-D35). |
| I-D9 | **Switching Automatum off during a flow undoes the flow** (mechanism replaced by I-D19): the game goes back to the event before the flow began (its own batches only, which ATW's undo rule always allows since nothing else could change meanwhile), then Automatum is off; the player redoes it by hand. Undone random results are asked again on redo; seen information stays seen. **Superseded by I-D19, then I-D52** (there is no switch). |
| I-D10 | **The game can be inspected during a flow:** an eye icon hides and shows the flow's overlays, and hold-to-inspect works on everything underneath. Only changes are blocked (D32), never viewing. |
| I-D11 | **Private and shared flows:** casting a spell and activating an ability are private — the acting client applies the steps locally and keeps the continuation locally, sending nothing until the cast completes; then everything (card to the Stack, choices, mana, targets) goes as one batch, and cancel/undo before that only drops local steps. Everything else (resolution, triggers, combat, steps) is shared — each step is sent as its own batch as it happens, so both players follow it and either may answer (D11). Which kinds are private is a table playtesting adjusts; the engine is the same either way. Costs accepted: nobody answers a private flow for the caster; local progress is lost if the app closes mid-cast (could be saved on the device later). **Changed by I-D56:** private flows stay; shared steps are events per acting point, and only the decider answers ("either may answer" is gone). |
| I-D12 | **Extra turns:** ATW's turn-change event names whose turn it is, so the engine's turn order (incl. extra turns, CR 500.7) maps onto it (owner, 2026-11-02). |
| I-D13 | **Stack entries without a card:** an ability whose source is gone (e.g. a delayed trigger of a resolved spell) is an ability-only Stack entry showing the ability's text (owner, 2026-11-02). |
| I-D14 | **Automated batches may exceed the 100-action cap** (e.g. up to 1000), so one engine call stays one all-or-nothing batch (SYS-010) even for board wipes and mass untaps (owner, 2026-11-02). **Superseded by I-D54:** there are no ATW batches; an event holds the engine's own changes. |
| I-D15 | **Turning Automatum on is refused** while the Stack holds manual entries or Temp piles are open, with a message saying why (owner, 2026-11-02). **Superseded by I-D52** (there is no switch). |
| I-D16 | **ATW's sideboard is "outside the game"** for the engine (companion, CR 702.139; CR 400.11a) (owner, 2026-11-02). |
| I-D17 | **The engine sees both hands** (owner, 2026-11-02): ATW doesn't hide information from clients, so the state a client builds has every hand card known; only library contents (ATW's unknown library order, filled by the server) and face-down cards stay unknown (D60). This lets the acting client pass or answer for an offline player where the rules leave them nothing to decide, with fewer hand-overs to the other player's view. **Changed by I-D54/I-D56:** the server and every device hold one full-information engine state (I-D27); passing or answering for an offline player is gone (only assumptions, I-D56 §3). |
| I-D18 | **One per-player setting, "Skip when I have no choice", on by default** (owner, 2026-11-02; replaces the separate automatic-passing setting of I-D3), stored per player in the game so the acting client follows the other player's choice. **On:** the engine passes priority and skips questions for that player whenever they have nothing to do — fastest, but a skip may reveal something about their hidden cards (e.g. "discard a land card or …" skipped because no land is in hand; a spell resolving at once because nothing in hand could respond). **Off:** when a pass or a skipped question depends on cards only that player can see (hand, face-down cards), the engine asks them instead (a priority window, or the question with nothing to choose, to dismiss). Things that never depend on hidden cards stay automatic either way (P5). The engine knows which cards each player can see, so it can tell when a skip depends on hidden ones. **Superseded by I-D56:** Auto-skip of the private response mode, run only on the player's own device; the shared state keeps `skipWhenNoChoice` off. |
| I-D19 | **Switching off during a flow reverts it on the server** (owner, 2026-11-02; replaces I-D9's use of undo): the switch sends a "revert flow" request; the server undoes the events back to the flow's start in order, whoever made them, as one dedicated server process (not a player's Undo, which only takes back the player's own events). **Superseded by I-D52** (there is no switch). |
| I-D20 | **The undo window keeps counting events** (owner, 2026-11-02); it may be raised if playtesting shows automated batches push a player's own actions (e.g. a life edit) out of reach. **Superseded by I-D56 §10:** free undo or an undo request; no event-count window. |
| I-D21 | **Deck card data is refreshed for Automatum** (owner, 2026-11-02): stored deck card data made before the new fields (`parts`, `colorIndicator`) is rebuilt from the catalog (a forced catalog/deck refresh if needed; decks may be wiped if a refresh can't be done). A card that still can't be read plays with its printed values and manual abilities instead of blocking the game. |
| I-D22 | **History events are natural branching points** (owner, 2026-11-02): the minimum is one event each time a player could take an action. Engine bookkeeping (restamps, ledgers, records) is folded into its batch's visible event, and a priority pass is shown only when a player passed themselves (automatic passes stay inside the event); timeline stepping skips what is folded. Today's many events come from the manual board not knowing what can be responded to; further event cleanup may follow from Automatum. **Changed by I-D56:** an assumed pass is an event of its own; a player's own device's passes fold into the event that reached them (HIS-092). |
| I-D23 | **No branching while a flow is open** (owner, 2026-11-02): starting a branch is refused, like other changes (D32). Since the pause review (decision A, to be confirmed): only from a point inside the flow; a choice open only on the live line is left behind with it. **Moot under I-D56:** branches start only where a real answer differs from an assumed one, at a decision point. |
| I-D24 | **Switching off clears the open flow** (reverted per I-D19) and keeps effect records, so their durations still apply when Automatum is switched on again; a manual "Clear Automatum data" action sits in the switch's hold panel (owner, 2026-11-02). **Superseded by I-D52** (there is no switch). |
| I-D25 | **Emblems** show as a chip by the player's life square with the emblem's text; playtesting decides whether other UI is needed (owner, 2026-11-02). |
| I-D26 | **Redo assigns fresh timestamps** when it re-applies an event, so stamp order follows real event order (owner, 2026-11-02; a starting point — undo/redo's final shape is decided by playtesting once Automatum is complete). **Superseded by I-D56:** redo is removed. |
| I-D27 | **Hidden information is about what is shown, not what the client receives** (owner, 2026-11-02): ATW clients may hold hidden identities (opponent's hand, face-down cards) in their data; what matters is that the UI never shows them to a player who shouldn't see them. Wherever the engine or the integration could either keep data from the client or just not show it, choose the path that is easiest to implement and maintain. |
| I-D28 | **Automatum on allows only what the engine considers legal; off allows any board manipulation** (owner, 2026-11-02). With Automatum on, manual board edits are not offered (e.g. the P/T corner shows the computed value and isn't editable; keywords in notes are just notes); each phase blocks the manual ways as the engine takes them over, until I4 where only engine-legal actions remain. With it off, the board can be changed in every current (and possible new) manual way. Switching back on does a best-effort recovery from the board and history (`EngineState.from`); what can't be recovered is lost and the game may then play differently — accepted. Example: "if you sacrificed a creature this turn" can't be known from a manual move to the graveyard, so it recovers as no sacrifice; "if a card left your graveyard this turn" can be read from manual moves (D33 tags), so it recovers. Refusing to switch on stays where the state would be unmanageable (I-D15). **Superseded by I-D52:** there is no off mode; only what the engine allows exists. |
| I-D29 | **Combat damage flow (I3)** (owner, 2026-11-02): in the declare-blockers step the table shows the damage that would happen with the suggested divisions, and players may respond; passing priority confirms. In the damage step the engine asks for the divisions (CR 510.1: attacker first, then defender, public): each is pre-filled with a suggestion and changeable when other legal divisions exist; automatic when the player has no choice and "Skip when I have no choice" is on; either player may accept for the other to keep async games moving (D11). UX speed-up: the defender may make and confirm their choice at the same time as the attacker, and sees whether the attacker is still deciding; the choices are still recorded and shown in rules order (attacker's first). Damage is then dealt at once (CR 510.2). **Changed by I-D56:** nobody accepts for the other player; an order-free division is answered with the suggestion for every player (§6 b), any other is its player's real decision. |
| I-D30 | **ATW's model and UI may change freely for Automatum** (owner, 2026-11-02): we don't retrofit the engine onto ATW's current design; ATW and its UI are modified and extended as Automatum needs. |
| I-D31 | **A first-strike combat damage step is its own step** in ATW (CR 510.4), added when it occurs. |
| I-D32 | **Combat area redesign** (owner, 2026-11-02): attackers and blockers get "drag here" slots with arrows showing who blocks whom (so one creature can block several attackers); with Automatum off a drag just moves a projection. Needs its own design session before it's built; until then Automatum combat uses today's lanes for one-to-one blocks. **Superseded by I-D38.** |
| I-D33 | **A "pre-event" system:** undoable early answers a player can give before their decision opens (e.g. the defender's damage division, I-D29), applied when the decision opens (owner, 2026-11-02). **Changed by I-D56 §6 (c):** early answers are only the decider's own, applied as engine-automatic answers when the decision opens. |
| I-D34 | **The move follows whoever must act** with Automatum on: the priority holder or the deciding player (owner, 2026-11-02). **Changed by I-D56 §7:** the move is worked out per viewer from their local head and next stop, never part of an event. |
| I-D35 | **Automatum events are acting points** (owner, 2026-11-02; extends I-D22): ideally each point where a player can act is one event, everything automatic before it (turn-based actions, triggers placed, state-based actions) folded into it. Automatum events may be entirely separate from manual events or combined events — whichever is simplest. **Changed by I-D56:** an assumed input always begins its own event. |
| I-D36 | **Drags are Automatum interactions while on** (owner, 2026-11-02; I-D28): dragging a land to the battlefield plays it, dragging a spell to the battlefield (or the Stack) casts it, and other drags map to the engine action they mean or are refused. |
| I-D37 | **Manual edits during a "do this by hand" step:** while the engine waits on a `Manual` decision, manual edits (P/T, counters, moves) are allowed until the player answers "done" — low priority; the goal is Automatum good enough that it never needs switching off (owner, 2026-11-02). **Superseded by I-D52:** there are no "do this by hand" steps. |
| I-D38 | **Combat area redesign** (owner, 2026-11-02; I-D32): owner-approved design in the combat redesign brief — one active target lane for staging attackers ("Rest → target"), tap-select/tap-assign blockers with auto-deselect after 1 (or N for "can block N"), arrows for every block with a gap between rows, selection highlights what a creature fights, preview stays during normal priority (no "let damage happen" prompt), damage division one dialog per pairing with a meaningful choice, modes "In order" (default, drag) and "Free" (steppers), skipped when no choice matters. |
| I-D39 | **No damage automation with Automatum off** (owner, 2026-11-02): with Automatum off players do everything by hand (the combat layout still communicates attacks and blocks); today's "Deal combat damage"/auto-resolve damage is removed. Automatum is the improved version of it. **The Automatum-off part is superseded by I-D52** (there is no off mode). |
| I-D40 | **Acting for the other player asks first** (owner, 2026-11-02; review item A): the step button or any priority pass made for the other player shows an explicit confirmation. Later maybe a game setting (before or during a game) to allow or forbid acting for the opponent. **Superseded by I-D56:** nobody acts for the other player; their answers are assumed (then confirmed or branched by their real answer) or waited for. |
| I-D41 | **Pause points and response windows** (owner, 2026-11-02; review item B): when the opponent does something you could react to, you're shown it with a short pause (1–3 s, progress bar) in which you can react easily. "Full control" (per player) adds pause points (e.g. your own spells). Both online: the reacting player may hold and think as long as they like; the acting player has a setting to proceed at once or to wait, but waits at most the response time. Opponent offline (async): the acting player never waits. Timeline playback with Automatum on stops at the same pause points, with no time limit. A reaction after the acting player moved on uses branching (a longer reaction time on one side than the other). Testing decides if it feels good. **Superseded by I-D56:** private response modes, decision stops in playback and the waiting bar; no response time, Hold or late-reaction branch. |
| I-D42 | **Switching Automatum on drops turn-scoped engine data** (owner, 2026-11-02; review item C): leftover combat, passes, waiting triggers and early answers are dropped — best effort. Automatum off is mainly a "bug → report → fix by hand → continue" escape and for un-cards; the goal is that people play with it on. Refined 2026-11-03 (final sync review #1, decided overnight, to be confirmed): the current combat stays while the lanes still show it; only stale combat is dropped. **Superseded by I-D52** (there is no switch). |
| I-D43 | **Logging for reproduction** (owner, 2026-11-02): engine and ATW Automatum logic log plenty, captured in error/problem reports, so a weird game situation can be reported, reproduced as an automated test and fixed. |
| I-D44 | **Automatum on by default for new games** (owner, 2026-11-03): a new game's first state has Automatum on, so both players see it on from the start; the New game dialog has an "Automatum" switch (on by default) to start a game without it. Existing games are unchanged. Built: `CreateInvitation.automatum` (and `ChallengeFromPod.automatum`; a pod challenge has no dialog and asks for on) is stored on the game (V51, `game.automatum`, false for existing games and when absent) and every play of the game starts with it (`StartRules.initialize(automatum)`). **Superseded by I-D52** (every game has Automatum; no switch). |
| I-D45 | **Toggling the switch asks first** (owner, 2026-11-03): tapping the Automatum switch shows a local "Turn Automatum on?" / "Turn Automatum off?" dialog with a short line on what it means; Cancel does nothing. Where turning on is refused (I-D15) the refusal shows at once instead, so there is one dialog, not two; turning off mentions an unfinished Automatum step or own cast it takes back. **Superseded by I-D52** (there is no switch). |
| I-D46 | **Playtest decisions (owner, 2026-11-03):** (a) castable hand cards and activatable permanents glow softly from behind (from the engine's options); (b) no refusal snackbars ("X can't be cast now") — the UI conveys it (no glow; a tap on an unplayable card gives a small shake; the reason is in Inspect); (c) with Automatum on players use only Automatum: the quick-actions row becomes Automatum toggles (Full control, Skip when I have no choice, Autotap mana) and there are no manual table actions; no "Manual…" entries at all (owner: the non-Automatum way to do things is switching Automatum off; keep Automatum play as simple as possible — Automatum off exists to recover a game from a bug or to use an unsupported card); during an open "do this by hand" step (I-D37) the direct gestures (drags, life/counter controls) work without any extra menu; (d) the step button uses MTG Arena-style wording that says what pressing it does ("Pass", "To combat", "Attack (2)", "No blocks", "Resolve", "End turn"), neutral colour. **Changed:** (c)'s toggles are now the private response mode, Always assume resolves and Autotap mana (I-D56); its Automatum-off and "do this by hand" parts are superseded by I-D52; (d)'s "Pass" acts only for the viewer (I-D56). |
| I-D47 | **Casting (owner, 2026-11-03):** "Autotap mana sources" (setting, on by default): double-tap (or drag) casts at once with the automatic payment; the cast panel appears only when there are real choices (modes, kicker/additional costs, X, targets) and has no mana selection. Mana already in the pool is used first, so to pay differently: undo, tap the wanted sources by hand (mana goes to the pool), cast again — autotap pays the rest. The panel: full width, docked exactly above the hand, shows the card's art small (hold = large Inspect overlay), the hide/show eye stays in the same place. Casting feels instant: the local prediction shows the result at once, the server confirms in the background (no spinner). | I-D48 | **Cards and buttons in Automatum panels (owner, 2026-11-03):** every card a panel or choice shows renders like a card on the battlefield — a small card you can drag, tap and hold to Inspect — never a text-only button; zones of a choice (e.g. Scry's Top / Bottom) are labelled areas the cards are dragged or tapped into. | I-D49 | **Rules-driven opening with Automatum on (owner, 2026-11-03):** game rules (hardcoded for now, later per-game settings): opening hand 7, one free mulligan, London mulligan (CR 103.5). | I-D50 | **Hand and table in Automatum mode (owner, 2026-11-03):** no hand context menu; hold = Inspect. Tapping a hand card raises it a little ("half a double-tap") and highlights the mana sources autotap would use; tapping it again casts/plays it. While raised, chips above it offer the ways to cast it, the regular cast first and selected, then each optional/alternative cost (kicker, flashback, evoke, offspring, …) with proper mana symbols: tapping a chip selects it (the highlighted sources update), tapping the selected chip again — or the card — casts it that way; unaffordable chips are disabled. | I-D51 | **Automatum support shown for card collections (owner, 2026-11-03):** a card is supported when the parser reads it fully with no "do this by hand" parts (worked out from its rules text on the device, per parser version — not a hand-kept list; the explicitly tested sets are listed in the libraries' READMEs). | I-D52 | **Automatum is always on — ATW becomes an MTG engine app (owner, 2026-11-03; supersedes the switch, I-D9/I-D15/I-D19/I-D24/I-D28/I-D37/I-D42/I-D44/I-D45 and the "Automatum off" parts of other decisions):** every game is played through Arcanum; there is no Automatum switch and no manual board manipulation (tabletop controls, manual menus and gestures, manual combat, the manual mulligan flow, tokens/dice/notes/pings/marks/links/counters by hand, "do this by hand" steps). | I-D53 | **Games the rules end (owner, 2026-11-03):** when the engine ends a game (a player at 0 life, a loss or draw by the rules, an agreed loop draw), the result is shown at once ("You won" / "You lost" / "Draw", depending on who views it) with one OK; either player may confirm. | I-D57 | **Assumptions are conditional pre-moves (owner, 2026-11-07; the concept behind I-D56's assumed answers, HIS-096, HIS-109):** conceptually an assumption is not deciding for the opponent; it is like leaving them a pile of instructions with conditions: one side says "if you block like this, turn this over", the next "then I cast Lightning Bolt on X". You pre-move on the condition that they answer as assumed; their real answer only ever chooses which of your instructions apply, and an assumption their real answer contradicts is as if it had never been written. The implementation does, and should, apply the assumed answer to the game state and branch when the real answer differs (automation is button presses, HIS-109; undo and branching rules as built) — but design decisions about assumptions (what may be assumed, what they reveal, how they show, what a later real answer does) follow the pre-move-with-conditions model, not "decide for your opponent, who may change it". |
